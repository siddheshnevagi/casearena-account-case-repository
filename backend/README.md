# Backend — Account Management & Case Repository

FastAPI + SQLAlchemy + PostgreSQL. See
[`../docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md) for why this stack was
chosen over the PRD's original Supabase assumption, and
[`../docs/API_CONTRACT.md`](../docs/API_CONTRACT.md) for the full endpoint
reference (also available live at `/docs` once the server is running).

## Requirements

- Python 3.12+
- PostgreSQL (via the included `docker-compose.yml`, or your own instance)
  — SQLite works for a zero-dependency smoke test, see below.

## Setup

```bash
cp .env.example .env          # edit if you're not using the default docker-compose Postgres
docker compose up -d db       # starts Postgres on localhost:5432
pip install -r requirements.txt
alembic upgrade head          # creates users/profiles/cases tables
uvicorn app.main:app --reload
```

The API is now at `http://localhost:8000`; interactive docs (Swagger UI) at
`http://localhost:8000/docs`, and the health check at `/health`.

### Running against SQLite instead of Postgres

For a quick local check without Docker, set in `.env`:

```
DATABASE_URL=sqlite:///./dev.db
```

Then `alembic upgrade head` and `uvicorn app.main:app --reload` as above.
This is fine for manual smoke-testing; the test suite already runs on
SQLite (see below), and CI runs migrations against a real Postgres service
to catch anything SQLite would silently paper over (native enums, JSON
column semantics, etc.).

### Running the full stack in Docker

```bash
docker compose up --build
```

This starts both Postgres and the API container together (see
`docker-compose.yml`). Run `alembic upgrade head` once against the
Dockerized Postgres before the API can serve real requests — the API
container does not run migrations automatically on boot, so a bad
migration never gets silently half-applied by a container restart.

## Running tests

```bash
pytest
```

Tests run against an isolated in-memory SQLite database per test (see
`tests/conftest.py`) — no external services required. They cover the
acceptance criteria in the PRD directly: `test_auth.py` (US-03 signup/
login/lockout), `test_profile.py` (onboarding, dashboard ordering),
`test_cases.py` (US-04 browse/search/filter, US-04B upload/share,
ownership restrictions, admin moderation).

## Project structure

```
app/
  main.py            FastAPI app instance, CORS, router wiring
  config.py           Settings (env-driven), see .env.example
  database.py          SQLAlchemy engine/session, Base
  models/               SQLAlchemy ORM models (User, Profile, Case)
  schemas/               Pydantic request/response models
  core/
    security.py           Password hashing, JWT issuing/verification
    deps.py                 get_current_user / get_current_admin dependencies
  services/
    storage.py            File storage abstraction (local disk, or S3/R2 — see STORAGE_BACKEND)
    cases.py                Shared case-presentation/matching helpers
  routers/
    auth.py                signup / verify / login / refresh / me
    profile.py               onboarding / profile / dashboard
    cases.py                  browse / upload / share / moderate
    account.py                 account deletion (ADR-03)
alembic/                Migrations — hand-written, not autogenerated (see
                         alembic/versions/0001_initial_schema.py's docstring)
tests/                 Pytest suite
scripts/
  promote_admin.py     CLI to grant admin rights (deliberately no API for this)
```

## Adding a migration

Autogenerate wasn't available while building this (no local Python/Alembic
CLI in the environment this was first written in — see the root README's
"Status and next steps"), so `0001_initial_schema.py` was hand-written to
mirror `app/models/*.py` exactly. Once you have a working Alembic CLI:

```bash
alembic revision --autogenerate -m "describe the change"
```

**Always review the generated file before committing** — autogenerate
misses some changes (renamed columns show up as drop+add, `SAEnum` `name=`
changes aren't detected, etc.) and this project pins explicit `name=` on
every `SAEnum` specifically so the Python model and the Postgres native
enum type never drift silently (see the comment in `app/models/case.py`).

## Environment variables

See `.env.example` for the full list with explanations. Nothing in the
codebase reads an environment variable that isn't listed there — if you add
one, add it to both `.env.example` and `app/config.py`'s `Settings` class in
the same commit.

## Deploying to production

See [`../docs/DEPLOYMENT.md`](../docs/DEPLOYMENT.md) for the full checklist
(managed Postgres, S3/R2 object storage, hosting the API, hosting the
frontend). The short version: never run this in production with
`DATABASE_URL=sqlite:...` or `STORAGE_BACKEND=local` — the first loses
durability guarantees the PRD assumes, the second silently loses every
uploaded PDF on the next redeploy.

## Integrating from Team 1 / Team 3

Read [`../docs/API_CONTRACT.md`](../docs/API_CONTRACT.md) first — it's the
maintained contract. In short:

- Validate this module's JWTs with the shared `JWT_SECRET_KEY` /
  `JWT_ALGORITHM` rather than calling back into this service per request.
- The case schema (`app/models/case.py`) is frozen per PRD §9 — read it,
  don't guess at field names from the frontend.
- `POST /cases/{id}/practice` is how Team 1 should report a completed
  practice session back to this module (powers "sort by most practised").
